Access control for the coupon platform

Every requisition, approval, and coupon-generation endpoint is open to anyone who can reach the API. This is the reasoning behind the fix, and how a role check actually reaches an endpoint.

Decision — Keycloak (OAuth2/OIDC) Owner — Backend
Context

The API has no authentication layer today. There is no User model, no login endpoint, and no role check anywhere in the codebase.

Concretely, that means the following are all reachable by anyone with network access to the service:

  • Requisitions — create, fulfill, auto-fulfill, or reject a depot's litres request
  • Approvals — approve or reject a transfer, confirm receipt at the destination
  • Coupons — generate single or bulk batches, force a state transition, transfer between locations
  • Configuration — change the bulk-generation limit, page-size limit, or coupon validity period
The gap Anyone who can reach the API can approve their own requisition, or mint coupons, with no record of who did it.
The decision

Keycloak issues tokens, Spring Security checks them

Keycloak runs as its own service and becomes the system of record for logins, passwords, and roles. It issues a signed JWT on login, with the user's roles carried as a claim inside the token. Spring Security's OAuth2 resource-server support verifies that token on every request — no custom login or token code lives in this application.

Two things about this project made Keycloak the better call over hand-rolling JWT auth in-house:

  • Single sign-on is already on the roadmap — Keycloak is built for exactly that, a self-issued token isn't.
  • The ERP integration already speaks OAuth2 — Keycloak is an OAuth2/OIDC provider natively, so it's the same protocol on both sides instead of two auth systems to reconcile later.
Why not self-issued JWT

Same validation step, different amount of code behind it

Spring Security validates a JWT the same way regardless of who signed it. The difference is everything that has to exist before that validation step — and who maintains it.

One title, several departments Approval isn't one queue — Stocks and Commercial each sign off on their own side of a transfer. The existing approve / confirm-receipt split already encodes this: the sending department ships (status goes to TRANSFERSHIPMENT), the receiving department confirms receipt (TRANSRECEIPT). The process document names Sales Executive as the approver for a requisition, but leaves the approver for the Coupon Transfer step itself blank — worth confirming whether that's the Stocks Controller by convention, or genuinely open.

Either way, a role claim alone can't express the department split — hasRole('APPROVER') says nothing about which department someone approves for. That needs a second piece of information alongside the role:

  • In Keycloak: one group per department (Stocks, Commercial, Retail, …), each carrying the roles above as composite roles. Group membership rides along in the token as a claim.
  • In Spring Security: the role annotation still gates the endpoint, but the service layer has to additionally check the token's department claim against the request's fromDepartment (for approve) or toDepartment (for confirm-receipt) — a data-level check @PreAuthorize can't do by itself, since it has no way to see which department a specific approval request belongs to.
Mobile client

The attendant app is a public client, not a trusted one

The RedemptionController /scan endpoint already exists for the attendant mobile app. That app runs on hardware Petrotrade doesn't fully control — a phone can be lost, rooted, or decompiled — so it needs a different Keycloak client setup than the backend or any internal web tooling.

Backend / internal web — confidential client

  • Holds a client secret, server-side only
  • Standard authorization-code flow

Attendant mobile app — public client

  • No client secret embedded in the app binary
  • Authorization Code + PKCE instead
  • Token stored in Keychain (iOS) / Keystore (Android)
Shared devices Station phones are often handed between shifts. A short access-token lifetime plus a PIN or re-login on app resume keeps a lost or shared handset from acting as whoever last logged in.
Effort

What actually needs Keycloak knowledge

One-time setup

  • Run Keycloak via Docker Compose
  • Create the realm, the department groups, and the roles above
  • Register one client for this API
  • Point Spring Security at the realm's issuer URI

Ongoing, per endpoint

  • @PreAuthorize("hasRole('APPROVER')")
  • Plain Spring Security — nothing Keycloak-specific
  • No login, token, or password code to maintain
Net effect The Keycloak-specific knowledge is front-loaded into a single setup session and doesn't recur in day-to-day endpoint work.
